# Release process

Added in phase 2b, wave D. A release publishes the pkl package and the runner binaries together, under the version in `pkl/PklProject`, as a GitHub **pre-release**. The pre-release flag is the gate (decision 46): promoting a release to a stable one is a separate step, described under "Promoting a release" below.

## Cutting a release

release-please owns the version, the changelog, the tag and the draft release. `release.yml` still builds, attests, verifies and publishes. Nothing is released until you merge the release pull request.

1. Merge ordinary pull requests with conventional titles (`.github/commit-types.txt`). On every push to `main`, `release-please.yml` keeps one release pull request up to date (title `chore(main): release <version>`). Below 1.0.0 a breaking change bumps the minor and `feat` or `fix` bump the patch (`release-please-config.json`). `chore`, `docs`, `ci`, `build`, `style` and `test` are hidden from the changelog and produce no release on their own; `refactor`, `perf` and `revert` are listed and give a patch.
2. The release pull request changes `version` in `pkl/PklProject` (its `x-release-please-version` comment marks the line), `CHANGELOG.md`, `version.txt` and `.release-please-manifest.json`. Raise `requiresRunner` in `pkl/Config.pkl` in a normal pull request first if the package needs a newer runner than the last release. A pre-release ranks below its release, so never require a runner version a pre-release of the same version cannot meet.
3. Before merging it, run the release workflow by hand on the release pull request's branch (Actions, release, Run workflow, choose the branch `release-please--branches--main--components--pantheon-scaffold`, `dry_run` left on). It tests the package, builds the runner on each of the three platforms, smoke tests each binary on its own platform and assembles `checksums.txt`, and attests and publishes nothing. The assembled files are kept for 7 days as the `release-assets` artifact.
4. Merge the release pull request. That is the go. `release-please.yml` then creates the tag `v<version>` and a **draft** release (`draft` and `force-tag-creation` in the config), both under the App token, so the tag push starts `release.yml`. The release job uploads the assets to the draft and publishes it as a pre-release (`.github/scripts/publish-release.sh`). The tag ruleset forbids moving or deleting a pushed tag.
5. After the release run, check it from the outside as for earlier releases, and promote it only on your own go (see "Promoting a release").

**The release files are rendered.** `release-please.yml`, `release-automerge.yml`, `release-bump.yml`, `.github/scripts/publish-release.sh` and `.github/scripts/release-bump.sh` are rendered from the Builtins by this repository's own `scaffold.pkl` (`releaseShape = "draft"`, `versionFile = "pkl/PklProject"`, `versionCommitScope = "pkl"`), the same way a consumer gets them (see [adopting.md](adopting.md#releasing-with-release-please)). Change them in the Builtins, not in the rendered files. `release.yml`, which builds the package and the runner, and `release-please-config.json` stay hand-written here.

**The fallback is a tag pushed by hand.** `git tag v<version> && git push origin v<version>` from the merged commit still works: with no draft for the tag, `publish-release.sh` creates the pre-release as it always did. release-please then does not know about that release: change `.release-please-manifest.json` to the released version in the same pull request that sets `version` in `pkl/PklProject`, or the next release pull request starts from the wrong version.

**After a release, `release-bump.yml` bumps the version.** `pkl project package` fetches the published package with the same version and refuses to build when the contents differ ("was already published with different contents ... bump the packages version"), so the package build in CI and several runner tests fail while `pkl/PklProject` holds a published version. When a release run has published and verified a plain `vX.Y.Z` tag (it runs from the `release` workflow, only on success), `release-bump.yml` opens the pull request `chore(pkl): start <next patch>` under the App token, waits until its checks have registered and passed, and squash-merges it. Release-please recomputes the version from the commits when it opens the next release pull request, so the bump only keeps `main` buildable in between. The version in `PklProject` is therefore always the next unreleased one, and the next tag is that version.

If it does not run or does not finish (a failed release gets none, a failing check or a timeout leaves the pull request open, an already higher version on `main` ends it with a notice in the step summary), bump `version` in `pkl/PklProject` by hand with the first pull request that changes anything under `pkl/`, as before. If the release pull request and a bump pull request both change the version line, release-please rewrites its own branch on its next run.

**The Monday merge of the release pull request is off.** `release-automerge.yml` runs when you press Run workflow. To let the Monday schedule merge a release pull request on its own, set the repository variable `RELEASE_AUTOMERGE_SCHEDULE` to `true` (Settings, Secrets and variables, Actions, Variables); unset or any other value, a scheduled run is skipped. There is a release pull request only when there are releasable commits, and merging it is the go for a release, so decide that before switching it on. A Monday merge can run next to a bump pull request; both end on `main` in either order.

**A job that fails on a 5xx from GitHub is safe to re-run.** Downloads from GitHub release URLs (the mise download in `mise-action`, or the published-version check that `pkl project package` makes) can return 504 during an outage, which fails the job before any of our code runs. The release workflow publishes nothing until its last two jobs, and it refuses a version that already has a release, so re-running it is safe. This is decision 81 of the plan: no retry code.

A version is never re-published. If a release is bad, cut the next patch version and add the bad version to `known-bad.json` on `main`.

**When a release does not finish.** The tag exists and cannot be moved. Look at what is left:

- The run failed before the release job (prepare, package, build, smoke): the draft release-please made is still there, with no assets. Re-run the failed jobs. The release job adopts the draft.
- The release job failed after uploading some assets: the draft holds them, and `gh release upload` refuses names that already exist. Delete the uploaded assets from the draft (or the draft itself, then create it again by hand with `gh release create --draft`), then re-run the release job. Never re-run after the release is published: the job stops, because a published version is never re-published.
- More than one draft carries the tag: the job stops. Delete the extra drafts.
- The release is published and `verify-release` failed: the build is bad. Cut the next patch version (a normal `fix:` pull request, then the release pull request) and list the burned version in `known-bad.json`. `pkl/PklProject` still holds the burned version until the next release pull request, so bump it by hand with the first pull request that changes anything under `pkl/`.
- Tags such as `v0.4.0-rc1` match `v[0-9]*`, but `check-tag` needs the tag to equal the `PklProject` version, so a release candidate tag is refused.

The rendered header of `release-please.yml` describes the Builtin for repositories without this setup (it says both crates and Cargo.lock, and that release-please may create the GitHub Release). Here the config makes release-please create a draft and `release.yml` publish it.

## What the workflow does

| Job | What it does | Permissions |
|---|---|---|
| tool | Builds the release tool (`crates/scaffold-release`, a Rust program) and uploads it as `scaffold-release`. It is a job of its own, with read permission and no token in its environment, because building runs the build scripts of every crate it depends on, and that must not happen next to a token that can write. `prepare` and `release` download the binary and check its sha256 against this job's output before they run it. | read |
| prepare | Runs the release tool: the tag must be `v<version>` and match `pkl/PklProject`. On a dry run, which has no tag, it also checks the tag this version would get (`v<version>`). A release for that tag must not exist yet. | read |
| package | The runner tests (`bun test`) and the package build (`pkl project package`). Uploads `package-files`. | read |
| build | One job per target, on a machine of that target (`ubuntu-latest`, `ubuntu-24.04-arm`, `macos-latest`): installs the pinned Rust toolchain, installs the tools through mise with `MISE_ENV=rust-build` (which adds `zig`, see `mise.rust-build.toml`), builds the release tool (`cargo build --release -p scaffold-release`, which it also uploads as `release-tool-<target>` for the smoke job, outside the `binary-*` files that are published), builds the Rust runner with `scaffold-release build-rust` (static musl on Linux, with `zig cc` compiling the C code) and uploads it as `binary-<target>`. | read |
| smoke | The 16 check smoke suite on linux-x64, linux-arm64 and darwin-arm64, each on the binary built for that target. | read |
| release | Downloads the release tool, `package-files` and the three binaries, cross-checks the package files, writes `checksums.txt` (with the release tool), attests every asset, publishes the pre-release with `publish-release.sh` (adopts the draft release-please made for the tag, or creates the pre-release when there is none). Attestation and publication run on a tag push only. | contents, id-token and attestations: write |
| verify-release | From the outside, on all three platforms: installs the runner through mise with `mise lock` and `mise install --locked` (checksums and provenance enforced), runs `gh attestation verify` on the downloaded `checksums.txt`, limits the lock to the supported platforms (`lockfile_platforms`) and checks that it names only the three runner binaries, renders and checks through the real package URI with the published checksum, and runs `upgrade --dry-run` against the real release. Phase 5: it also renders the whole standard set (`Builtins.standardWorkflows` and `standardFiles`, imported from the same package URI) into an empty folder, runs `check`, and renders again expecting "written 0 file(s)" | read |

`checksums.txt` lists the three binaries, the package metadata file (its checksum is the one pkl checks with `::sha256`) and the zip. The attestation covers the binaries, the package files and `checksums.txt`.

`verify-release` is the first place the real download, `gh attestation verify` and mise's provenance check meet the code that `upgrade` and `mise install` rely on. It runs after publication, so a failure leaves a published pre-release: say so, cut the next patch version, and list the failed one in `known-bad.json`.

## Safety properties

They are asserted by `crates/scaffold-package-tests/tests/release_workflow.rs` and kept honest by `archive/spikes/phase-2b-wave-d/mutate.ts`:

- Only a `v[0-9]*` tag push or a manual run starts it, never `pull_request_target`.
- Every job asks for its own permissions, and only `release` can write.
- Every action is pinned by SHA, no secrets are used, checkouts keep no credentials.
- Tag names, refs and inputs reach scripts through `env`, never through `${{ }}` inside `run`.
- A manual run is a dry run unless told otherwise.

## Promoting a release

Added in phase 8. A release stays a pre-release until it is promoted. The promotion is the workflow `promote.yml`, run by hand from `main`, and it is the only thing that edits a release. It never changes the assets: it removes the pre-release flag, drops "(pre-release)" from the title and "Pre-" from the first words of the notes.

Since Phase 2 of the Rust port ([ts-tooling-rust-port.md](ts-tooling-rust-port.md)) the tool is the Rust crate `crates/scaffold-release` (`scaffold-release promote check <tag>` and `promote promote <tag>`). A `tool` job builds it with read permission and no token, and the other jobs download it and check its sha256. The TypeScript tool and the `implementation` input that chose it were deleted in Phase 6, after v0.4.0 was released and promoted by the Rust tools. If the Rust tool misbehaves on a real promotion, the way back is to revert that change: the files are in git history.

1. **Dry run.** Run `promote` with the tag (for example `v0.1.5`) and `dry_run` left true. One job runs every guard and edits nothing. It never touches the environment.
2. **Real run.** Run it again with `dry_run` false. The first job repeats the guards, then the `promote` job runs in the environment `promote`. That environment has no protection rules today, so the job starts at once (see "Who approves" below). It runs every guard again, edits the release, and checks the result.

The guards, all before the edit (`crates/scaffold-release/src/promote.rs`, with tests and a mutation check):

| Guard | Refuses when |
|---|---|
| Run from main | the workflow runs on any ref other than `refs/heads/main` |
| Tag shape | the tag is not `v<major>.<minor>.<patch>[-pre-release]` |
| Release state | the release is a draft, or is already stable (a published version is never re-published) |
| Assets | the release does not carry exactly the files a release carries |
| Attestation and digests | `checksums.txt` has no valid attestation, or any file's digest differs from it |
| Known bad | the version is in `known-bad.json` |
| Release run | the release workflow did not succeed for the tag, or its verify job is missing or not successful |

After the edit it checks that the release is stable and the latest, that `checksums.txt` is byte for byte the one attested before, that every digest still matches, and that the attestation still verifies (decision 46's revisit trigger: promotion must not change the asset bytes or the checksums).

The tag is not compared with `pkl/PklProject`: on `main` that file always holds the next unreleased version, so the comparison would refuse every older candidate.

**Who approves.** Nobody, today. The environment `promote` has **no protection rules** (decision 91, 09-11-2026): the owner decided that a required reviewer would block the work while the repository has one contributor. The job still names the environment, and GitHub creates a missing environment with no rules on its first use, so the job runs as soon as it is dispatched. The environment then records each promotion as a deployment, and it does not gate it.

What controls a promotion until a second contributor exists:

- it is dispatched by hand, from `main`, by someone with write access to the repository (the owner);
- every guard in the table above, run twice (once in each job), and the post-edit checks;
- the run itself, in the Actions tab, with its log.

This is a recorded accepted risk and not an approval of any kind: nothing is checked by a second person (decisions 78, 90 and 91).

### Before onboarding a contributor

Do this **before** the new contributor, collaborator, organisation member or bot with write access can dispatch a workflow here, and at the latest before the next promotion. It takes about five minutes and changes no code, because the workflow already names the environment.

1. Open the repository's Settings, then Environments, then `promote` (the environment exists after the first real promotion run. If it does not, click "New environment", name it `promote`, and click "Configure environment").
2. Tick "Required reviewers" and pick **a person who is not the maintainer**. Leave "Prevent self-review" ticked, so that whoever dispatches a promotion cannot approve it.
3. Under "Deployment branches and tags", choose "Selected branches and tags", add the rule `main`, and click "Add rule".
4. Click "Save protection rules".
5. Check it: `gh api repos/pantheon-org/pantheon-scaffold/environments/promote --jq '[.protection_rules[]|.type]'` must list `required_reviewers` and `branch_policy`.
6. Run `promote` once as a dry run: the first job passes and the second is skipped, so the check does not need an approval. The first real promotion afterwards waits for the reviewer.
7. Record it: add a dated line under "Releases so far" and in the plan, with who the reviewer is, and say the independent approval is now in place (it ends decision 91's accepted risk).

Also settle, in the same change, the other places where the maintainer is the only check: a required approving review on `main` and the creation of release tags (see "Accepted risks and open items").

## Bumping the pr-agent image

The `pr-agent.yml` workflow runs `docker://pragent/pr-agent@sha256:...`, the digest of a `*-github_action` tag. A docker reference has no 40-character commit, so it is not in `pkl/Pins.pkl` and neither the pin update workflow nor Dependabot moves it. Bump it by hand in `pkl/Tools.pkl` (`prAgentImage`), when the upstream tag moves or when a model in the default providers (`prAgentProviders` in `pkl/Config.pkl`) is retired by its vendor: the workflow is advisory, so a retired model fails without any check turning red, and the first sign is a pull request with no review. Check the digest is that of the multi-arch image (a manifest list), run the package tests, render, and refresh the baseline (`crates/scaffold-release/baseline/README.md`).

## Accepted risks and open items

- **No Security review.** The owner recorded P.3 as an accepted risk on 07-11-2026 (decision 78). Security has not reviewed this pipeline or the pkl flags, and no Security reviewer is named. This is a recorded risk, not an approval.
- **The Rust build downloads crates and a C compiler.** `cargo build --locked` takes the versions in `Cargo.lock`, which `cargo-deny` checks for advisories, licences and sources in CI. The C code of `ring` is compiled by `zig cc`, a version of Zig that mise pins and checksums in `mise.rust-build.lock` and that only the release-binary jobs install (the Ubuntu archive is not used: when its DNS failed on the runners on 11-11-2026, every Rust binary job failed with it). The pipeline downloads its other tools through mise too. All of these are supply-chain inputs for any later Security review.
- **No second reviewer, and no approval step.** The repository has one contributor. The owner recorded on 09-11-2026 that no second person approves the promotion (decision 90) and that the environment `promote` has no protection rules (decision 91). The steps to add them are under "Before onboarding a contributor" and are due before a second contributor can dispatch a workflow.
- **The tag ruleset has no creation rule**, so anyone with write access can push a `v*` tag. Today that is the maintainer only.
