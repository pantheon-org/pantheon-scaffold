# Proof of the v0.1.3 release candidate against the four repositories

This is the Phase 7 proof report. Wave A (tasks 7.1 and 7.2) is below; the other waves are appended as they run (upgrade, downgrade and detach; the throwaway-repository run; the benefit test; the security dossier and the sign-off).

## How to read it

`runner/scripts/proof-render.ts` loads the **published** package of the release candidate through its real `package://` URI and checksum, with the **published** runner, whose attestation and digest it verifies first. For each repository it takes the files the package renders and puts each one in exactly one category, by rules written before the run (`runner/scripts/proof-categories.ts`, tested in `runner/test/proof-categories.test.ts`, 17 tests, and a mutation check in `tmp/phase-7-wave-a`, 12 of 12 rules caught). A difference no rule names is **UNCATEGORISED** and fails the proof. A run with a deliberately wrong skill name for one repository failed with three uncategorised files and exit 1, so the proof can fail.

| Category | Meaning |
|---|---|
| identical | The rendered file is the repository's file, byte for byte, with the same mode |
| comments and formatting only (P.1) | Parsed YAML is equal, `run:` scripts are byte for byte equal, no directive comment was lost |
| pin moved | As above, and an action commit moved since the repository last updated it (the pin update workflow keeps the package current) |
| recorded difference | A difference the plan accepted: decisions 74 and 87 (`.gitignore`), 85 (`dist-workspace.toml`), 86 (`dependabot.yml`), and the skill auditor's seeded `SECURITY.md`. Each rule checks the difference is only the accepted one |
| migration | What adopting the package changes once: `mise.toml` (10 lines added, 4 removed) and `hk.pkl` replaced by the seeded one (decision 31) |
| mode change only | `sync-labels.sh` becomes executable (decision 79) |
| new file | A file the package adds that the repository does not have yet |

The first render without `--force` refuses every existing file that differs, which is the safe default; the table is the adoption rendered with `--force`. Nothing is written to the repositories: the clones are in a temporary folder.

Notes on the scenarios:

- **Pin-back is two steps by design.** `upgrade 0.1.1 --force` moves the pins, and the render that follows is refused with exit 3 because the package is older than the one that last rendered (the version rule of [runner-lifecycle.md](../../../docs/runner-lifecycle.md)). The consumer then renders once more with `render --force`, and the files are byte for byte the 0.1.1 render again. `upgrade` does not pass `--force` on to the render, because `--force` would also overwrite hand edits.
- **A package that drops or renames a file needs a clean tree.** The runner deletes an orphan only from a clean tracked tree, so the consumer commits the config change and then renders. After `upgrade` the pins are changed and uncommitted, so if the new package drops a file the render is refused (exit 3) until the pin change is committed, and then `render` finishes the job.
- **`detach` keeps every rendered file** as a plain file and removes the manifest; a `git revert` of the detach commit brings the manifest back, and `check` passes and a render writes nothing.

Checked against the real release: the fixed `upgrade` took the same scratch consumer from 0.1.1 to 0.1.3, moved 1 import, rendered with exit 0, and `check` passed. The fix is in the runner, so it ships in the next candidate (0.1.4). 0.1.3 stays published; whether it goes on the known-bad list is decided when 0.1.4 exists (decision 88).
